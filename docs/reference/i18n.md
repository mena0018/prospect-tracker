# Internationalization (fr / en)

How locale is detected, how URLs are localized, and how to add translatable copy.
Library: **Paraglide JS** (compiler-based). Rationale for the choice:
[`docs/decisions/0002-i18n-library.md`](../decisions/0002-i18n-library.md).

## How it fits together

Four pieces, all wired in the setup commit:

- **Vite plugin** ([`vite.config.ts`](../../vite.config.ts)) compiles `messages/{locale}.json`
  into typed ESM functions under `src/i18n/paraglide/` (gitignored, regenerated on build). It
  also owns the locale `strategy`.
- **URL patterns** — none are configured, so Paraglide's default applies. Custom
  `urlPatterns` must be set in `project.inlang/settings.json`, not only in `vite.config.ts`:
  the `i18n:compile` CLI (run by `pretypecheck`) reads the settings file and would otherwise
  overwrite the plugin's output with the default.
- **Server middleware** ([`src/server.ts`](../../src/server.ts)) wraps the request so the
  locale is resolved (cookie / `Accept-Language`) and available during SSR.
- **Router rewrite** ([`src/router.tsx`](../../src/router.tsx)) strips the `/en` prefix before
  matching routes (`deLocalizeUrl`) and re-adds it on generated links (`localizeUrl`). The
  route tree stays prefix-free — no locale segment in `src/routes/`.

`<html lang>` in [`__root.tsx`](../../src/routes/__root.tsx) reads `getLocale()`.

## Locale strategy

`strategy: ['url', 'cookie', 'preferredLanguage', 'baseLocale']` — resolved in order:

1. **url** — the `/fr` or `/en` prefix wins when present.
2. **cookie** — `PARAGLIDE_LOCALE`, set when the user switches language.
3. **preferredLanguage** — the browser `Accept-Language` header.
4. **baseLocale** — falls back to `fr` (the product's primary market).

The **base locale is not prefixed**: French serves from the bare path (`/app`, `/login`) and
English from `/en/app`. This is Paraglide's default — its compiler skips the base locale when
building the default URL patterns — and the usual SEO recommendation: the primary market's
pages stay canonical at the root, with one indexable URL per language instead of a duplicate
`/fr` mirroring `/`.

### The url strategy needs a client-side redirect to actually win

Paraglide's native `url` strategy is **client-only** — its resolver skips `url` when
`isServer` is true. So at the first (SSR) render, `url` is skipped and the **cookie** decides:
`/en/login` with a `PARAGLIDE_LOCALE=fr` cookie would be served in French, defeating the
prefix.

The fix (from the official TanStack example) is a client re-resolve in the root `beforeLoad`
([`__root.tsx`](../../src/routes/__root.tsx)):

```ts
if (typeof window !== 'undefined') {
  const decision = await shouldRedirect({ url: window.location.href })
  if (decision.redirectUrl) throw redirect({ href: decision.redirectUrl.href })
}
```

After hydration `url` applies, `shouldRedirect` sees the mismatch and redirects to the URL's
locale — so the prefix wins and the cookie is updated to match. Without this hook the cookie
silently overrides the URL.

**Known limit:** this only covers client-side navigations. On a _direct_ hit (typed URL,
external link) with a conflicting cookie, the server answers `307` to the cookie's locale
before the client can re-resolve — so `/en/x` with a `fr` cookie still lands on `/x`.
Making the URL win there too would need a custom server-side strategy.

### Why `src/server.ts` passes the original `req`

TanStack Router already de-localizes the URL via its `rewrite`. If the middleware also
de-localized the request passed to the handler, both would strip the prefix and cause a
redirect loop. So the middleware runs for locale detection / cookies only, and the handler
receives the untouched `req`.

## Adding translatable copy

1. Add the key to **both** `messages/fr.json` and `messages/en.json`. Namespace with an
   underscore prefix by domain: `auth_signIn`, `opportunities_new`, `errors_notFound`.
   (Underscore, not dot — dotted keys force `m["a.b"]()` bracket access; underscores give the
   clean `m.a_b()` call.)
2. Use it: `import { m } from '@/i18n/paraglide/messages'` then `m.auth_signIn()`.
3. Parameters: `"greeting": "Bonjour {name}"` → `m.greeting({ name })`. Typed — a missing or
   misspelled param is a compile error.

The plugin recompiles on save (HMR); `pnpm i18n:compile` regenerates manually (runs in
`pretypecheck`, so CI always has fresh output).

Need the locale type or a guard? Paraglide generates them — import from the runtime, don't
hand-write: `type Locale`, `locales`, `isLocale`, `baseLocale`, `assertIsLocale`.

## Adding a localized route

Nothing to declare: with the default URL patterns every route is localized automatically —
add the file under `src/routes/` and it is served at `/path` (fr) and `/en/path` (en).

Per-route pathname translation (`/en/settings` → `/fr/parametres`) would need explicit
`urlPatterns` in `project.inlang/settings.json`, using Paraglide's full-URL form
(`:protocol://:domain(.*)::port?/en/...`). Plain paths like `/en/login` are silently ignored.

## Translating Zod validation messages

Pass the message as a **function**, never a string:

```ts
// ✅ called at validation time — picks up the request's locale
email: z.email({ error: () => m.validation_emailInvalid() })

// ❌ evaluated once at import — locale frozen at server boot
email: z.email(m.validation_emailInvalid())
```

A schema module is imported once per process. On the server `getLocale()` reads an
AsyncLocalStorage filled **per request** by the middleware, so a message resolved at import
time has no request context and yields the wrong locale for everyone. Zod calls the function
form on every parse, which is what makes it correct.

> **Do not "simplify" this by calling the message.** The eager form _works in dev_ — Vite
> re-evaluates modules on HMR, so the locale looks correct every time you check. It only
> breaks in production, where the module is loaded once and every message stays in the boot
> locale (`fr`) forever. The users who see it are the ones whose screen you never look at.

Schemas import from **`zod/v4`** (not `zod`, which resolves to the v3 API): the `error` option
is typed to accept an error map function there, whereas v3 types `message` as a plain string.

## Errors across the RPC boundary

Server functions send **codes**, never translated messages:

```ts
// server
if (!updated) throw appError('NOT_FOUND') // Error('NOT_FOUND')

// client
toErrorMessage(error) // → looks the code up, calls m.error_notFound()
```

Only `error.message` survives a `createServerFn` throw — custom properties, the subclass and
any status set with `setResponseStatus()` are all dropped — so the code rides in that field.
Translating on the server instead would break the client's lookup: it
compares what it receives against a known set, and a string translated in one locale cannot be
matched against a catalogue built in another. An unrecognised code falls back to the generic
server message so internals never leak.

`ERROR_MESSAGES` stores the message **functions**, not their results — same lazy rule, and the
same dev-only-looks-fine trap, as the Zod schemas above.

## Two setup traps (already handled)

- **`vite.config.ts` cannot use the `@/` alias** — Node loads it before Vite resolves aliases.
  Any import there must use a relative path.
- **Plugin order** — `tanstackStart()` must precede `viteReact()`; the router plugin runs
  before JSX transformation, otherwise the dev server refuses to start.

## Constraints (kept the setup stable)

- Uses the **manual middleware** integration, not the experimental generated server entry —
  no version-pinning or `routeStrategies` restrictions.
- Paraglide is strongest when keys are static (known at build time); that's our case — copy
  lives in components. Dynamic/CMS-driven keys are an explicit non-use-case.
